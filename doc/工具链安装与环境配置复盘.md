# RustDesk Android 工具链安装与环境配置复盘

## 背景

本次目标是在 Windows 11 上 fork RustDesk，并构建一个 Android viewer-only 自用 APK：手机只作为控制端连接 Windows 电脑，不作为被控端暴露屏幕共享、无障碍输入、悬浮窗、录音、开机自启等能力。

用户要求工具链安装到 D 盘，不要散落到根目录。因此最终约定的本地目录是：

```text
D:\02_Agent\24_RustDesk
├── rustdesk
└── toolchains
```

其中：

- `rustdesk`：GitHub fork 的本地 clone。
- `toolchains`：JDK、Flutter、Android SDK/NDK、Rust、Gradle、CMake、Ninja、vcpkg、OpenSSL、libsodium 等构建工具。

## 为什么这次花了大量时间

RustDesk Android 构建不是单一 Flutter 项目构建，而是跨了多套工具链：

- Flutter/Dart：移动端 UI 与 Android APK 打包。
- Gradle/Kotlin：Android 原生宿主、Manifest 合并、插件注册、资源链接。
- Rust/Cargo：核心 RustDesk 逻辑、FFI 动态库。
- cargo-ndk/NDK/Clang：Windows 主机交叉编译 Android `arm64-v8a` native library。
- bindgen/libclang：生成和验证 C/C++ 绑定。
- vcpkg/CMake/Ninja/MSYS/NASM/Perl：构建 FFmpeg、aom、libvpx 等 C/C++ 依赖。
- OpenSSL/libsodium：Rust native 依赖需要 Android 目标库，不能混用 Windows host 库。

这次耗时主要来自以下几个点。

## 主要耗时点

### 1. 没有现成 Android 构建环境

初始环境里缺少或没有稳定暴露以下工具：

- `java`
- `flutter`
- `cargo`
- Android SDK
- Android NDK
- Gradle
- CMake
- Ninja
- cargo-ndk
- vcpkg Android 依赖

RustDesk 仓库也没有可直接复用的 Gradle wrapper，所以不能简单执行 `gradlew assembleDebug` 结束。

### 2. RustDesk 对版本比较敏感

RustDesk 当前 Android 构建更接近 CI 预期环境：

- Flutter `3.24.5`
- Rust `1.75.0`
- cargo-ndk `3.1.2`
- Android NDK r28c，也就是本机安装的 `28.2.13676358`
- Android SDK build-tools `30.0.3` 和 `34.0.0`

版本漂移会引出 Gradle、Kotlin、Flutter、NDK、Rust crate 之间的连锁问题。所以正确方式不是随手装最新版，而是尽量贴近仓库和 CI 版本。

### 3. Windows 交叉编译 Android 比 Linux/macOS 更麻烦

Windows 上交叉编译 Android Rust native library 时，需要同时处理：

- `aarch64-linux-android22-clang.cmd`
- `llvm-ar.exe`
- `ANDROID_NDK_HOME`
- `PKG_CONFIG_PATH`
- `OPENSSL_DIR`
- `CARGO_ENCODED_RUSTFLAGS`
- MSYS 工具路径
- vcpkg host/target triplet

如果任意一个路径指向 Windows host 库，或者缺少 Android target 库，就会出现链接或 build script 失败。

### 4. vcpkg/bootstrap 和源码下载受网络影响

vcpkg 需要下载和构建多项 Android C/C++ 依赖，例如：

- `ffmpeg`
- `aom`
- `libvpx`
- `libyuv`
- `opus`
- `oboe`
- `cpu-features`
- `pkgconf`

期间遇到过下载、bootstrap、代理、源码包命名变化等问题。为了继续推进，最终使用了 GitHub release 里的 `vcpkg.exe`，并对部分 portfile 做了兼容修补。

### 5. OpenSSL 和 libsodium 不能混用 host/target

Rust 构建中有 host build script，也有 Android target library。最容易踩坑的是：

- 把 Android `SODIUM_LIB_DIR` 设成全局变量，会污染 host build script。
- `build.rs` 如果依赖 `hbb_common`，会间接拉起 libsodium，导致 host/target 混用。
- OpenSSL vendored 构建在 Windows + Android 交叉环境下容易被 Perl/MSYS/路径问题卡住。

最终处理方式：

- 手动构建 Android arm64 OpenSSL。
- 手动构建 Android arm64 libsodium。
- 不设置全局 `SODIUM_LIB_DIR`。
- 用 `CARGO_ENCODED_RUSTFLAGS` 给 Android target 添加 `-L native=...libsodium...`。
- 改造 `build.rs`，避免 build dependency 拉入 `hbb_common`。

### 6. bindgen 遇到 Android 下 VPX/AOM opaque struct

Android 目标下，`vpx_codec_dec_cfg_t` 和 `aom_codec_dec_cfg_t` 通过 bindgen 表现为 opaque struct，不能按原字段初始化。

最终处理方式：

- Android viewer-only 不需要本机屏幕编码，所以 VPX/AOM encoder 在 Android 下改成 viewer-only stub。
- Decoder 初始化不再构造 cfg struct，改为传 `ptr::null()` 使用库默认配置。
- `scrap::codec::test_av1()` 不在 Android/iOS 调用。

### 7. Flutter 插件会重新合并权限和组件

即使主 Manifest 删掉权限，Flutter 插件也可能通过 manifest merge 重新带入：

- Camera
- Image picker provider
- QR scanner activity
- Storage/media permissions
- Foreground service
- Notification
- Wakelock

所以必须检查最终 APK，而不是只看源码 Manifest。

### 8. Debug APK 和 release APK 的签名路径不同

早期为了快速自测，曾先构建 debug APK：

```text
flutter\build\app\outputs\flutter-apk\app-debug.apk
```

debug APK 会使用 debug 签名，适合早期权限和组件验证；最终长期自用产物应使用自己的 keystore 构建 release APK，并重新做同样的权限、组件、签名和字符串检查。

## 关键经验

### 经验 1：先搭工具链，再做代码裁剪

Android Manifest 裁剪看似简单，但最终要以 APK 为准。没有完整工具链，就无法确认 Flutter 插件是否重新合并权限，也无法确认 dex 里是否还保留 host-only 类。

### 经验 2：先构建 native library，再构建 Flutter APK

当前自用 viewer-only Android APK 依赖 `libdeskviewer.so`。正确顺序是：

```text
cargo ndk native build
复制 libdeskviewer.so/libc++_shared.so
flutter build apk
apkanalyzer/aapt 验证
```

### 经验 3：不要全局设置 target-only 库路径

特别是：

```text
SODIUM_LIB_DIR
```

如果把 Android target libsodium 设成全局变量，会污染 host build script。更稳的是把 Android target 链接路径放进 `CARGO_ENCODED_RUSTFLAGS`。

### 经验 4：Manifest 删除不等于 APK 删除

需要同时检查：

- Manifest 权限
- Manifest 组件
- dex 类名
- APK 内资源和 native library

本次就发现过：Manifest 已经没有 `MainService`，但 dex 里仍编译进了 host Kotlin 类。最终通过 Gradle/Kotlin source exclude 解决。

### 经验 5：Flutter 插件依赖要一起清

如果只隐藏 UI，不移除依赖，APK 里仍可能有：

- QR scanner activity
- Image picker provider
- 相机 feature
- GET_CONTENT query
- 相关 dex 类

本次最终移除了：

- `qr_code_scanner`
- `zxing2`
- `image_picker`
- `XXPermissions`

### 经验 6：viewer-only 应优先选择 no-op，而不是新增权限

比如 `WAKE_LOCK`：保留它可以让远控期间更容易保持亮屏，但会增加权限面。当前目标是尽量少拿手机权限，所以 Android viewer-only 下让 `WakelockManager` no-op，不再声明 `WAKE_LOCK`。

### 经验 7：本机路径不要写死进可提交配置

`.cargo/config.toml` 最初写死了 D 盘 NDK 路径。更稳的写法是只写工具名，让 PATH 和环境变量决定实际位置：

```toml
[target.aarch64-linux-android]
linker = "aarch64-linux-android22-clang.cmd"
ar = "llvm-ar.exe"
```

### 经验 8：最终产物必须单独做 release 验证

debug APK 适合早期验证权限、组件和功能。真正长期自用时，必须单独处理 release signing：

- 创建自己的 keystore。
- 配置 `key.properties`。
- 构建 release APK。
- 再做同样的权限、组件、签名、RPATH/RUNPATH 和解包字符串检查。

### 经验 9：Rust/C/C++ 路径需要同时 remap

`llvm-strip` 不能清理所有 panic/source path。Rust crate、OpenSSL、Opus 等依赖可能把源码路径编进 release `.so`。最终做法是：

```text
RUSTFLAGS: --remap-path-prefix=旧路径=中性路径
CFLAGS/CXXFLAGS: -ffile-prefix-map=旧路径=中性路径
```

如果只 remap Rust，不 remap C/C++，`llvm-strings libdeskviewer.so` 仍可能看到 vcpkg/OpenSSL/Opus 的构建路径。

### 经验 10：Flutter 打包也需要 Cargo 在 PATH

即使 native `.so` 已经手动构建完成，`flutter build apk` 阶段的 Gradle 脚本仍会通过 `cargo metadata` 查找 `rustls-platform-verifier-android` 的 Maven 仓库。因此 release 打包时 `PATH` 里仍必须包含：

```text
D:\02_Agent\24_RustDesk\toolchains\rust\cargo\bin
```

否则会在 `flutter\android\build.gradle` 的 `project.evaluationDependsOn(':app')` 阶段报 `A problem occurred starting process 'command 'cargo''`。

## 安全边界

本流程只做透明自用 fork、权限最小化、组件裁剪和构建验证。不做反检测、伪装规避、加壳、签名欺骗或隐藏远控行为。即使最终权限很少，自签名远控类 APK 仍可能被 Play Protect 或手机安全软件提示风险，这不能通过技术规避来承诺消除。
